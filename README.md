# BYTE BACK 방어전 시작 틀 R5

이 저장소는 1단계에서 학생 본인이 GitHub 저장소와 Vercel 배포를 만드는 출발점입니다. 포함된 메모 네 건은 가상 자료입니다. 실제 학생 자료, 토큰, 비밀키를 넣지 마세요.

## 학생이 하는 일: 세 걸음

1. GitHub 계정을 만듭니다.
2. 방어전 1단계 카드의 **Deploy** 버튼을 누릅니다. Vercel에 GitHub로 로그인하고, 새 저장소가 **본인 계정의 Public 저장소**인지 확인한 뒤 Deploy를 누릅니다.
3. 배포가 끝나면 화면에 나온 `https://…vercel.app` 주소를 방어전 1단계 카드에 붙여넣고 제출합니다. 저장소 주소나 설정 파일은 적지 않습니다.

배포가 끝나면 `/`에서 점령된 가상 자료실을 볼 수 있습니다. `/data.json`에는 같은 가상 메모가 공개됩니다. 이 공개 상태를 확인하는 것이 1단계의 출발점입니다. 1단계 접수와 심판 판정은 포털에서 확인합니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`과 `publicAppUrl`은 이전 제출 묶음 방식의 자리표시자입니다. 1단계에서는 학생이 편집하지 않습니다. 2단계 이후 코딩 도구가 필요한 설정과 보호 기능을 단계별로 작성합니다. `npm run bundle`과 `bundle-notes.json`도 1단계의 세 걸음에는 포함되지 않습니다.

로컬에서 가상 화면만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다. 저장소의 `src/attack-check.mjs`는 실제 배포가 된 뒤 `/data.json`을 비로그인으로 요청해 공개 가상 메모의 확인 표시를 읽습니다.

## 다음 단계의 코딩 도구에 전달할 규칙

[AGENTS.md](AGENTS.md)를 먼저 읽히고 한 번에 한 제작 단위만 요청하세요. 2단계부터는 자료 보호를 구현할 때 `public/data.json`을 복사하는 1단계 빌드 흐름도 함께 바꿔야 합니다. 3단계 이후의 로그인, 허용 경로, 5단계의 원본 API 주소, 6단계 이후 정책 규칙은 해당 단계 원고와 계약에 맞춰 추가합니다. 비밀번호·토큰·서버 전용 키·실제 학생 기록을 코드, Git, 제출 묶음에 넣지 않습니다.

`src/decider.mjs`와 `src/detect.mjs`의 로컬 시험은 반 엔진이나 운영 심판의 결과가 아닙니다. 1단계 이후 제출 묶음 계약 `aleph.defense.submission.v2`는 `scripts/bundle.mjs`에 남아 있으며, 코딩 도구가 해당 단계의 최신 배포 주소와 Git 원격을 맞춘 뒤 사용합니다.

## 8단계 저장점 준비: 자료별 접근 구역

- 메모는 `memo:<id>`, 로그인 후 읽는 가상 강사 공지는 `announcement:stage8-notice-1`로 표시한다. 가상 공지에는 실제 강사 자료 본문이 없다.
- 판정기는 단일 메모와 공지의 GET 요청 경로만 허용한다. 메모 전체 목록, 공지 쓰기, 강사 자료와 알 수 없는 경로는 거부한다.
- 6단계 기기 등록 판정과 7단계 복합 이상 접속 추가 확인은 유지한다. 현재 요청 계약에 없는 `role`이나 소유자 정보를 판정기에 넣지 않는다.
- 메모 API는 기존의 검증된 사용자 ID와 DB `owner_id` 조건을 사용한다. 목록과 새 메모도 검증된 사용자 ID 범위에서 처리한다.

### 확인한 범위
- Windows PowerShell에서 `npm.cmd run decider:test`의 기존 네 가상 검사가 통과했다.
- 로컬 가상 요청에서 개별 메모 조회는 allow, ID 없는 전체 목록은 deny로 확인했다.
- 단계 4에서 확인한 A/B 계정의 교차 메모 요청 거부를 이번 변경 이후 실제 배포에서 다시 시험한 것은 아니다.
- Preview 배포는 서버 비밀 환경 변수가 없어 공지 요청이 SERVICE_NOT_CONFIGURED를 반환했다. 운영 배포의 비로그인 공지 조회 401과 공지 POST 405는 확인했다. 로그인한 공지 조회와 당시의 운영 심판 세부 판정은 여기서 확인하지 않았다.
- `route_not_allowed` 거부 사유 코드가 운영 등록부에서 허용되는지는 아직 확인하지 않았다.

### 다시 확인하는 방법
1. `npm.cmd run decider:test`와 `npm.cmd run fixture:7`로 기존 판정을 확인한다. 이는 로컬 가상 검사다.
2. 운영 배포 후 로그인 상태에서 자기 메모와 가상 공지를 읽고, 비로그인 공지 요청 및 POST 요청의 거부를 확인한다.
3. 서로 다른 시험 계정으로 직접 메모 API를 요청하여 자기 자료의 정상 조회와 다른 계정 자료의 거부를 재확인한다.
4. 배포 상태와 점검 결과를 확인한 뒤 `npm.cmd run bundle`로 제출 묶음을 생성한다. 실행하지 않은 확인을 완료했다고 기록하지 않는다.


## 9단계 저장점 준비: 조회 폭주 탐지

### 구현한 기능
- `src/detect.mjs`는 로컬 사건 계약의 UTC 시각, 요청 종류, 가명 주체 ID만 읽고 나머지 필드를 탐지 결과에 저장하거나 출력하지 않는다.
- 같은 가명 주체의 GET 사건이 어느 10분 구간에서든 120건을 넘으면 `{ action: 'propose_revocation', reasonCode: 'burst_read', subject }`를 반환한다. 정확히 120건, 다른 주체의 합산, 10분 밖 사건은 탐지하지 않는다.
- 이는 회수 **제안**일 뿐이며 기존 `decide(request)`의 허용·거부 응답이나 서버 API의 권한을 변경하지 않는다.
- `aleph.config.json`의 단계는 9로 올리고 배포 주소·발급자·기존 허용 경로를 유지했다. `src/attack-check.mjs`는 8단계의 실제 HTTP 점검을 9단계에도 수행한다.

### 직접 확인한 결과
- `npm run detect:test`의 가상 사건 6건과 `npm run decider:test`의 기존 가상 판정 4건이 통과했다.
- 예시 사건에 메모·토큰 필드를 섞어도 정리된 입력에는 시각·GET·가명 주체만 남는 것을 로컬에서 확인했다.
- 이 검사는 로컬 연습이다. 실제 운영 사건 전달, 접속 회수, 심판 판정을 확인한 결과는 아니다.

### 남은 입력 계약 차이
- 단계 화면에는 낯선 네트워크와 갑작스러운 대량 조회의 **복합 조건**, 특정 가상 기기의 회수 제안이 적혀 있다.
- 현재 `docs/DETECT_EVENTS.md`의 사건에는 `at`, `method`, `identity.sub`만 있고 네트워크·기기 ID·접속 판정이 없다. 따라서 현재 구현은 문서의 조회 폭주 규칙까지만 검증했으며 화면의 복합 조건과 기기 단위 제안을 구현했다고 주장하지 않는다.
- 기기·네트워크의 검증된 사건 형식이 제공되면 이 차이를 해소해야 한다.

### 다시 확인하는 방법
1. `npm.cmd run detect:test`, `npm.cmd run decider:test`를 실행한다.
2. 최신 배포의 `/aleph.json`에서 단계 9와 커밋을 확인한다.
3. 실제 HTTP 점검과 설정을 확인한 뒤 `npm.cmd run bundle`로 제출 묶음을 만든다.

## 10단계 저장점 준비: 안전 사본에서 복구

### 정책 비교와 제한적 복원
- `node scripts/policy-preview.mjs`는 실제로 통과한 9단계 커밋 `bcf605d`의 `src/decider.mjs`를 SHA-256으로 검증하고, 현재 파일과 달라진 줄의 범위만 보여 준다. 정책 코드 본문이나 비밀값은 출력하지 않는다. 검증된 커밋이 없거나 해시가 다르면 중단한다.
- 비교에서 차이가 있다면 `node scripts/policy-restore.mjs`로 다시 미리 본다. 복원은 표시된 `currentSha256`을 `--expect-current-sha=`에 전달하고 `--apply`를 붙일 때만 작동한다. 이 절차는 `src/decider.mjs` 한 파일만 바꾸고, 변경 전 파일과 실행 기록을 Git에서 무시하는 `private-restore-audit/`에 보관한다. 다른 서비스 파일이나 기존 감사 이력은 삭제하지 않는다.
- 현재 정책은 안전 커밋과 해시가 같아 복원을 실행하지 않았다. 별도의 임시 복사본에서 정책을 바꾼 뒤 비교·해시 불일치 차단·한 파일 복원·감사 기록 보존을 확인했다.

### B 메모 한 건의 비공개 복구 경로
- `POST /api/restore-note`는 로그인 토큰을 검증한다. 요청은 `{ "id": "...", "ownerId": "...", "contentSha256": "..." }`만 받는다. 메모 본문과 개인키를 요청에서 받거나 응답하지 않는다.
- **침해 전 검증된** B 메모 사본을 비공개 JSON 파일에 `id`, `ownerId`, `title`, `body` 네 항목으로 준비해야 한다. `node scripts/backup-digest.mjs <비공개 파일 경로>`는 내용을 출력하지 않고 `SHA-256(JSON.stringify([id, ownerId, title, body]))`만 계산한다. 사본과 해시는 Git에 넣지 않고 배포 서비스의 비밀 환경 설정 `ALEPH_RESTORE_BACKUP_JSON`, `ALEPH_RESTORE_EXPECTED_SHA256`에 각각 입력한다. 현재의 변조된 DB 자료를 신뢰할 사본으로 사용하면 안 된다.
- 서버는 사본의 내용과 고정된 해시, 요청의 ID·소유자·해시, 검증된 B 사용자 ID를 대조한다. 모두 맞을 때만 그 ID의 레코드를 수정하거나 다시 넣는다. 다른 소유자의 같은 ID가 있으면 중단하고, 다른 메모나 감사 기록을 삭제하지 않는다. 사본이 없거나 검증에 실패하면 중단한다.
- `npm.cmd run restore:test`에서 사본 불일치, A 요청 거부, B의 지정한 한 건 복원, 정상 메모 보존, 소유자 충돌 중단을 가상 DB로 확인했다. 실제 비공개 사본이 제공되지 않아 실제 B 메모 복원과 복원 후 A/B 계정 검사는 **미실행**이다.

### 복원 뒤 순서대로 재확인
1. 먼저 정책 비교를 실행하고 검증된 사본과 변경 범위를 확인한다. 실제 차이가 있을 때만 정책 한 파일을 복원한다. `npm.cmd run decider:test`, `npm.cmd run fixture:7`로 6~8단계 규칙을 다시 확인한다.
2. 신뢰할 B 메모 사본과 별도로 기록해 둔 해시가 맞는 경우에만 로그인한 B 계정으로 복구 POST를 실행한다. B의 대상 메모 ID·소유자·내용을 사본과 대조한다. 사본이 없으면 복구를 시도하지 않는다.
3. A/B 각 계정에서 자기 메모 정상 조회, 상대 메모 조회·수정·삭제 거부를 확인한다. 가상 공지의 로그인 읽기와 쓰기 거부, 등록·미등록 기기 판정, 복합 이상 접속의 추가 확인, 조회 폭주 탐지를 순서대로 확인한다. `npm.cmd run detect:test`도 다시 실행한다.
4. 비로그인 메모·복원 경로의 거부, 정적 `/data.json` 비노출, 배포 `/aleph.json`의 단계·커밋을 확인하고 `npm.cmd run bundle`을 실행한다. 아직 실제 계정으로 확인하지 않은 항목은 완료로 기록하지 않는다.
