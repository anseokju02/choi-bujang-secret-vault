# BYTE BACK 방어전 시작 틀 R5

이 저장소는 1단계에서 학생 본인이 GitHub 저장소와 Vercel 배포를 만드는 출발점입니다. 포함된 메모 네 건은 가상 자료입니다. 실제 학생 자료, 토큰, 비밀키를 넣지 마세요.

## 학생이 하는 일: 세 걸음

1. GitHub 계정을 만듭니다.
2. 방어전 1단계 카드의 **Deploy** 버튼을 누릅니다. Vercel에 GitHub로 로그인하고, 새 저장소가 **본인 계정의 Public 저장소**인지 확인한 뒤 Deploy를 누릅니다.
3. 배포가 끝나면 화면에 나온 `https://…vercel.app` 주소를 방어전 1단계 카드에 붙여넣고 제출합니다. 저장소 주소나 설정 파일은 적지 않습니다.

배포가 끝나면 `/`에서 점령된 가상 자료실을 볼 수 있습니다. `/data.json`에는 같은 가상 메모가 공개됩니다. 이 공개 상태를 확인하는 것이 1단계의 출발점입니다. 1단계 접수와 심판 판정은 포털에서 확인합니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`과 `publicAppUrl`은 이전 제출 묶음 방식의 자리표시자입니다. 1단계에서는 학생이 편집하지 않습니다. 2단계 이후 코딩 도구가 필요한 설정과 보호 기능을 단계별로 작성합니다. `npm run bundle`과 `bundle-notes.json`도 1단계의 세 걸음에는 포함되지 않습니다.

로컬에서 가상 화면만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다. 저장소의 `src/attack-check.mjs`는 실제 배포가 된 뒤 `/data.json`을 비로그인으로 요청해 공개 가상 메모의 확인 표시를 읽습니다.

## 다음 단계의 코딩 도구에 전달할 규칙

[AGENTS.md](AGENTS.md)를 먼저 읽히고 한 번에 한 제작 단위만 요청하세요. 2단계부터는 자료 보호를 구현할 때 `public/data.json`을 복사하는 1단계 빌드 흐름도 함께 바꿔야 합니다. 3단계 이후의 로그인, 허용 경로, 5단계의 원본 API 주소, 6단계 이후 정책 규칙은 해당 단계 원고와 계약에 맞춰 추가합니다. 비밀번호·토큰·서버 전용 키·실제 학생 기록을 코드, Git, 제출 묶음에 넣지 않습니다.

`src/decider.mjs`와 `src/detect.mjs`의 로컬 시험은 반 엔진이나 운영 심판의 결과가 아닙니다. 1단계 이후 제출 묶음 계약 `aleph.defense.submission.v2`는 `scripts/bundle.mjs`에 남아 있으며, 코딩 도구가 해당 단계의 최신 배포 주소와 Git 원격을 맞춘 뒤 사용합니다.

## 8단계 저장점 준비: 자료별 접근 구역

- 6단계 기기 등록 판정과 7단계 복합 이상 접속 추가 확인은 유지한다. 현재 요청 계약에 없는 `role`이나 소유자 정보를 판정기에 넣지 않는다.
- 메모 API는 기존의 검증된 사용자 ID와 DB `owner_id` 조건을 사용한다. 목록과 새 메모도 검증된 사용자 ID 범위에서 처리한다.

### 확인한 범위

## 9단계 저장점 준비: 조회 폭주 탐지

### 구현한 기능
- `src/detect.mjs`는 로컬 사건 계약의 UTC 시각, 요청 종류, 가명 주체 ID만 읽고 나머지 필드를 탐지 결과에 저장하거나 출력하지 않는다.
- 같은 가명 주체의 GET 사건이 어느 10분 구간에서든 120건을 넘으면 `{ action: 'propose_revocation', reasonCode: 'burst_read', subject }`를 반환한다. 정확히 120건, 다른 주체의 합산, 10분 밖 사건은 탐지하지 않는다.
- 이는 회수 **제안**일 뿐이며 기존 `decide(request)`의 허용·거부 응답이나 서버 API의 권한을 변경하지 않는다.
- `aleph.config.json`의 단계는 9로 올리고 배포 주소·발급자·기존 허용 경로를 유지했다. `src/attack-check.mjs`는 8단계의 실제 HTTP 점검을 9단계에도 수행한다.

### 직접 확인한 결과
- `npm run detect:test`의 가상 사건 6건과 `npm run decider:test`의 기존 가상 판정 4건이 통과했다.
- 예시 사건에 메모·토큰 필드를 섞어도 정리된 입력에는 시각·GET·가명 주체만 남는 것을 로컬에서 확인했다.
- 이 검사는 로컬 연습이다. 실제 운영 사건 전달, 접속 회수, 심판 판정을 확인한 결과는 아니다.

### 남은 입력 계약 차이
- 단계 화면에는 낯선 네트워크와 갑작스러운 대량 조회의 **복합 조건**, 특정 가상 기기의 회수 제안이 적혀 있다.
- 현재 `docs/DETECT_EVENTS.md`의 사건에는 `at`, `method`, `identity.sub`만 있고 네트워크·기기 ID·접속 판정이 없다. 따라서 현재 구현은 문서의 조회 폭주 규칙까지만 검증했으며 화면의 복합 조건과 기기 단위 제안을 구현했다고 주장하지 않는다.
- 기기·네트워크의 검증된 사건 형식이 제공되면 이 차이를 해소해야 한다.

## 10단계 저장점 준비: 안전 사본에서 복구

### 정책 비교와 제한적 복원
- `node scripts/policy-preview.mjs`는 실제로 통과한 9단계 커밋 `bcf605d`의 `src/decider.mjs`를 SHA-256으로 검증하고, 현재 파일과 달라진 줄의 범위만 보여 준다. 정책 코드 본문이나 비밀값은 출력하지 않는다. 검증된 커밋이 없거나 해시가 다르면 중단한다.
- 비교에서 차이가 있다면 `node scripts/policy-restore.mjs`로 다시 미리 본다. 복원은 표시된 `currentSha256`을 `--expect-current-sha=`에 전달하고 `--apply`를 붙일 때만 작동한다. 이 절차는 `src/decider.mjs` 한 파일만 바꾸고, 변경 전 파일과 실행 기록을 Git에서 무시하는 `private-restore-audit/`에 보관한다. 다른 서비스 파일이나 기존 감사 이력은 삭제하지 않는다.
- 현재 정책은 안전 커밋과 해시가 같아 복원을 실행하지 않았다. 별도의 임시 복사본에서 정책을 바꾼 뒤 비교·해시 불일치 차단·한 파일 복원·감사 기록 보존을 확인했다.

### B 메모 한 건의 비공개 복구 경로
- `POST /api/restore-note`는 로그인 토큰을 검증한다. 요청은 `{ "id": "...", "ownerId": "...", "contentSha256": "..." }`만 받는다. 메모 본문과 개인키를 요청에서 받거나 응답하지 않는다.
- **침해 전 검증된** B 메모 사본을 비공개 JSON 파일에 `id`, `ownerId`, `title`, `body` 네 항목으로 준비해야 한다. `node scripts/backup-digest.mjs <비공개 파일 경로>`는 내용을 출력하지 않고 `SHA-256(JSON.stringify([id, ownerId, title, body]))`만 계산한다. 사본과 해시는 Git에 넣지 않고 배포 서비스의 비밀 환경 설정 `ALEPH_RESTORE_BACKUP_JSON`, `ALEPH_RESTORE_EXPECTED_SHA256`에 각각 입력한다. 현재의 변조된 DB 자료를 신뢰할 사본으로 사용하면 안 된다.
- 서버는 사본의 내용과 고정된 해시, 요청의 ID·소유자·해시, 검증된 B 사용자 ID를 대조한다. 모두 맞을 때만 그 ID의 레코드를 수정하거나 다시 넣는다. 다른 소유자의 같은 ID가 있으면 중단하고, 다른 메모나 감사 기록을 삭제하지 않는다. 사본이 없거나 검증에 실패하면 중단한다.
- `npm.cmd run restore:test`에서 사본 불일치, A 요청 거부, B의 지정한 한 건 복원, 정상 메모 보존, 소유자 충돌 중단을 가상 DB로 확인했다. 실제 비공개 사본이 제공되지 않아 실제 B 메모 복원과 복원 후 A/B 계정 검사는 **미실행**이다.

### 복원 뒤 순서대로 재확인
1. 먼저 정책 비교를 실행하고 검증된 사본과 변경 범위를 확인한다. 실제 차이가 있을 때만 정책 한 파일을 복원한다. `npm.cmd run decider:test`, `npm.cmd run fixture:7`로 6~8단계 규칙을 다시 확인한다.
2. 신뢰할 B 메모 사본과 별도로 기록해 둔 해시가 맞는 경우에만 로그인한 B 계정으로 복구 POST를 실행한다. B의 대상 메모 ID·소유자·내용을 사본과 대조한다. 사본이 없으면 복구를 시도하지 않는다.
3. A/B 각 계정에서 자기 메모 정상 조회, 상대 메모 조회·수정·삭제 거부를 확인한다. 가상 공지의 로그인 읽기와 쓰기 거부, 등록·미등록 기기 판정, 복합 이상 접속의 추가 확인, 조회 폭주 탐지를 순서대로 확인한다. `npm.cmd run detect:test`도 다시 실행한다.
4. 비로그인 메모·복원 경로의 거부, 정적 `/data.json` 비노출, 배포 `/aleph.json`의 단계·커밋을 확인하고 `npm.cmd run bundle`을 실행한다. 아직 실제 계정으로 확인하지 않은 항목은 완료로 기록하지 않는다.

## 11단계 저장점: 설치 화면과 기기 확인

### 동작과 경계
- 같은 HTTPS 자료실 주소에 설치 manifest, 192·512 아이콘과 설치 안내를 추가했다. 서비스 워커는 공개 오프라인 안내 페이지 **한 개만** 저장한다. 로그인 응답, 메모, 기기 증명, 개인키, 토큰 및 온라인 자료실 화면은 오프라인 저장소에 넣지 않는다.
- 기존 이메일 로그인 후 `/api/device`로 기기 상태를 조회한다. 승인 전에는 자료 화면을 표시하지 않으며, 등록한 기기를 WebAuthn으로 확인한 뒤 서버가 승인된 인증 수단인지 판단한다. 첫 기기는 로그인한 계정에서 기기 귀속 인증 수단을 생성하고 서버 검증을 통과해야 등록된다. 두 번째 기기부터는 등록된 인증 수단의 선행 확인도 필요하다.
- 서버는 5분 유효한 도전을 생성하고 사이트 주소·도전 값·사용자 확인 및 기기 귀속 여부를 검증한다. 서버가 가진 Supabase Auth `app_metadata`에 공개키와 기기 상태를 저장한다. 기기의 개인키는 코드나 웹 저장소에 넣지 않는다. 검증 후에는 기기·계정에 묶인 15분 유효 `HttpOnly; Secure; SameSite=Strict` 쿠키를 발급한다. 로그인 전환·로그아웃 시 쿠키를 지우며, 메모 목록·개별 메모·가상 공지·복구 API는 매 요청마다 서버의 현재 등록 상태를 확인한다. 거부되면 HTTP 403이다.
- `src/decider.mjs`는 교육 엔진의 `deviceRegistered` 등 기존 18개 입력 계약만 읽는다. 앱의 WebAuthn 등록부를 교육 엔진의 기기 등록부로 임의 변환하거나 브라우저의 `approved` 값을 판정기에 주입하지 않는다. **이 자료실에서의 기기 확인과 교육 엔진의 기기 등록은 별개의 연동 범위**이다. 엔진 등록 API 계약이 없어 엔진 쪽 실제 기기 승인 완료를 주장하지 않는다.

### 다시 실행하고 확인하기
1. 새 복사본에서 `npm ci`, `npm run build -- --local`, `npm run device:test`, `npm run decider:test`를 실행한다. 로컬 기기 시험은 가상 DB와 생성한 시험용 인증 응답을 사용하며 실제 학생의 기기를 승인했다는 증거가 아니다.
2. 배포 `/manifest.webmanifest`, `/icons/icon-192.png`, `/offline.html`, `/aleph.json`을 확인한다. 설치 후 네트워크가 끊긴 상태에서는 공개 안내 화면만 보여야 한다.
3. 본인 계정에서 승인 전 메모 목록·개별 메모·공지 API의 거부, 첫 기기 등록 후 기존 메모 정상 조회, 재접속 후 등록 기기 재확인, 다른 기기에서 비밀번호만으로 새 기기 등록을 시도했을 때 거부를 확인한다. 이 실제 기기 검사는 로그인 자격 증명과 호환 기기가 있는 학생이 브라우저에서 직접 수행해야 한다.
4. 실제 배포를 확인한 뒤 `npm run bundle`로 제출 묶음을 생성한다. 번들의 비로그인 요청과 로컬 시험을 승인된 학생 기기의 브라우저 검증 결과로 바꿔 기록하지 않는다.

### 확인 범위와 한계
- 최초 기기 등록은 유효한 계정 로그인과 기기 귀속 WebAuthn 증명에 기반한다. 별도 관리자의 수동 승인을 구현한 것은 아니다. 동기화된 패스키는 물리적으로 하나의 기기를 확인할 수 없어 등록에서 제외한다.
- 이 단계의 로컬 암호 검증·기존 판정 시험과 비로그인 배포 점검은 직접 실행한 범위대로만 기록한다. 실제 계정으로 기기 등록과 승인 후 자료 조회, 엔진의 실제 기기 등록 및 운영 심판의 판정은 별도로 확인해야 한다.

## 12단계 저장점: 탈환 작전실

### 출처와 구현 범위

| 구성 | 출처와 실행 결과의 범위 |
| --- | --- |
| 신원·기기·경로를 확인하고 판정을 받는 운영 서비스 | **제공된 ALEPH SDP 엔진**. 운영 심판의 요청·사건·회수 기록은 이 저장소에서 자동으로 읽을 수 없다. |
| `src/decider.mjs` | **학생 판정 규칙**. `docs/DECIDER_REQUEST.md`의 엔진 확인 입력만 사용하며 `device_registered`, `step_up_required`, `resource_route_policy` 세 규칙을 구현한다. 로컬 가상 요청의 허용·거부·추가 확인은 운영 심판의 판정이 아니다. |
| `src/detect.mjs` | **학생 탐지 규칙**. 같은 가명 주체의 GET이 10분 안에 120건을 넘으면 `propose_revocation`을 반환한다. `docs/DETECT_EVENTS.md`와 `npm run detect:test`는 로컬 가상 사건 계약이다. 실제 사건 전달과 접속 회수 집행은 확인되지 않았다. |
| 접속 알림·회수 | 별도의 운영 알림 기록이나 회수 집행 경로는 **연결·검증되지 않았다**. 화면에 ‘미확인’으로 표시한다. 로컬 탐지 제안을 실제 차단으로 표현하지 않는다. |
| 로그인 자료실·기기 확인·작전실 | **학생 웹앱**. `/api/auth`, `/api/device`, `/api/notes`, `/api/announcements/:id`, `/api/restore-note`는 기존 서버 API다. `/api/operations`는 공개 가능한 규칙 이름·배포 정보와 **운영 기록의 부재**만 제공한다. 메모 본문·토큰·사본·개인키를 돌려주지 않는다. |
| 복구 | 학생 구현 `src/restore-note.mjs`와 `scripts/policy-preview.mjs`·`scripts/policy-restore.mjs`. 작전실의 **배포 커밋**은 검증된 사본 버전이나 실제 복구 성공을 뜻하지 않는다. 사본 버전·복구 이력이 없으면 ‘미확인/미실행’이다. |

### 설치와 실행

1. 검토할 Git 커밋을 고정하고 공개 저장소 `https://github.com/anseokju02/choi-bujang-secret-vault`를 새 폴더에 받아 `npm ci`를 실행한다. Node.js 22 이상을 사용한다. 외부 계정·비밀값은 저장소에서 복사하지 않는다.
2. `npm run build -- --local`, `npm run operations:test`, `npm run decider:test`, `npm run fixture:7`, `npm run detect:test`, `npm run restore:test`, `npm run device:test`를 실행한다. 이는 코드·가상 사건의 로컬 시험이며 실제 엔진·심판 검사가 아니다.
3. 이미 배포된 `https://choi-bujang-secret-vault-y9nh.vercel.app/`와 `/aleph.json`을 열고 `step`, 커밋 SHA, 저장소 주소가 검사 대상과 일치하는지 확인한다. 화면의 ‘탈환 작전실’은 로그인 없이 보이지만 보호 자료는 기존 로그인·승인 기기 검사 뒤에만 보인다.
4. 새 배포를 만들 때는 `vercel.json`의 `npm run build`·`public` 설정을 사용한다. 서버에는 `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`(로그인)와 `SUPABASE_SECRET_KEY`(서버 전용 검증·DB)가 필요하다. 값은 서버 설정 화면에만 입력한다. 로그인 발급자·주소·WebAuthn 사이트 바인딩을 새 주소에 맞추고 기존 배포와 분리해 검증해야 한다. 값 자체를 Git, README, 점검 JSON에 적지 않는다. 안전 사본 복구에는 별도로 검증한 `ALEPH_RESTORE_BACKUP_JSON`·`ALEPH_RESTORE_EXPECTED_SHA256`가 필요하지만 이 저장소에 포함하지 않는다. 새 배포에서의 로그인·기기 등록은 수행했다고 주장하지 않는다.

### 실제 HTTP 증빙 만들기

1. 새 커밋이 배포된 뒤 `npm run operations:check`를 실행한다. 이 명령은 `aleph.config.json`의 배포 주소에 안전한 공개 정상 요청과 비로그인 금지 요청을 보내고, 응답 HTTP 상태·학생이 생성한 `X-Check-Id`·UTC 확인 시각을 `artifacts/stage12-http-evidence.json`에 기록한다. `artifacts/`는 Git에서 제외된다. 점검 ID는 **학생 자체 점검 ID**이며 운영 엔진의 요청 ID가 아니다.
2. 자료실 화면의 **지금 확인** 버튼으로 같은 표를 볼 수 있다. 등록 기기에서 로그인·승인을 마친 경우에는 본인 메모 목록, 강사 공지, 기기 승인 API의 HTTP 200도 확인한다. 승인되지 않은 기기로 로그인한 경우에는 메모 API의 HTTP 403을 확인한다. 토큰·응답 본문은 표에 넣지 않는다. 화면의 **결과 JSON 저장**을 누르면 상태·점검 ID·시각만 로컬로 내려받는다.
3. 표의 ‘기대와 일치’는 *그 요청의 실제 HTTP 응답*을 뜻한다. 1~11단계 모든 보안 규칙의 통과, 운영 엔진의 판정, 복구 완료를 뜻하지 않는다. A/B 교차 소유권·원본 API 직접 접근·실제 기기 등록·이상 접속 재확인·실제 회수·B 메모 복구·운영 심판 **41종 공격 시험**은 별도 실행 기록이 없으면 **미실행**으로 남긴다. 401 비로그인 거부만으로 소유권 거부를 입증하지 않는다.
4. 실제 계정으로 A/B 본인 정상 요청과 상대 소유 자료 거부를 시험할 때에는 각 계정이 직접 승인한 기기에서 수행하고, 두 요청의 HTTP 상태·점검 ID·UTC 시각만 기록한다. 자료 제목·본문·토큰·이메일은 증빙에서 제외한다. 41종 시험 결과는 포털 심판의 실제 실행과 판정이 나온 뒤에만 별도로 갱신한다.

### 복구와 재현의 경계

- 정책 훼손이 의심되면 `node scripts/policy-preview.mjs`로 검증된 커밋과 현재 파일의 해시·차이를 먼저 비교한다. 차이가 있는 경우에만 `node scripts/policy-restore.mjs`의 미리 보기 및 `--expect-current-sha=... --apply` 절차를 사용한다. 다른 파일과 기존 자료는 지우지 않는다. 이전에 검증된 상태라면 실행하지 않는다.
- B 메모 복구는 별도 보관한 신뢰할 사본·해시가 맞고 B의 본인 요청이 검증될 때 한 건만 수행한다. 사본이나 소유자 증거가 없으면 복구 POST를 실행하지 않는다. 복구한 다음 A/B 정상·거부 요청과 판정·탐지·설치 경로를 재확인한다.
- 저장점의 `aleph.config.json`은 단계 **12**이며 `judgeIssuer`는 제공된 주소를 그대로 유지한다. `npm run bundle`은 배포된 같은 커밋을 확인한 후 실행해 `artifacts/submission.json`을 만든다. 제출 묶음의 자체 HTTP 점검은 운영 심판 41종 시험과 별개의 증빙이다.

## XDR 웹 주입 보너스

`xdr/README.md`의 웹 주입 실습 기록을 따른다. 저장소 루트에서 `node xdr/web-injection/read-alerts.mjs`, `npm run xdr:run -- web-injection`, `node xdr/web-injection/respond.mjs` 순서로 다시 실행할 수 있다. 수업용 경보 26건의 로컬 판정은 block 8건, alert 9건, record 9건이다. 로그와 만료 시각이 있는 거부 후보는 Git에서 제외되며 실제 ZTNA 거부는 연결되지 않았다. 운영 심판의 판정은 포털 제출 후에만 확인할 수 있다.
